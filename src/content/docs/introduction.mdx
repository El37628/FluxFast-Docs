FluxFast helps you build a React interface without turning your frontend into a second application
server. FastAPI remains the place where URLs, permissions, validation, and data ownership live.
FluxFast **1.2.0** provides both a Next.js rendering shell and a standalone React/Vite SSR host.
FluxFast connects either host to FastAPI with the same versioned envelope and reactive resource
stores. The [version guide](/FluxFast-Docs/version-guide/) explains matched package installation
and upgrades from earlier stable releases.

If you have used Inertia, the first request will feel familiar: the server chooses a component and
sends its data. FluxFast extends that model by making data resources independently versioned,
cacheable, deferrable, and live.

## The mental model

Think in three layers:

<Steps>
1. **A page selects the interface.** A FastAPI route chooses an allowlisted frontend component. The
   URL and access checks stay in Python.
2. **Resources carry application data.** A page declares which resources it needs. Each resource has
   its own contract, version, loader, cache policy, and optional live behavior.
3. **The adapter renders stores.** The host resolves the selected component from a generated registry.
   React hooks read resource stores and re-render when those stores change.
</Steps>

This separation matters because pages and data do not always share the same lifetime. A navigation
can reuse an unchanged viewer resource, defer an expensive report, and subscribe to a live counter
without replacing the entire page payload.

## What each layer owns

| Concern | Owner | Why |
| --- | --- | --- |
| URL routing and route parameters | FastAPI | One authoritative routing table |
| Authentication and authorization | FastAPI | Decisions occur before protected data is serialized |
| Input and output contracts | Pydantic | Python definitions generate the frontend contract |
| Resource lifecycle and invalidation | FluxFast runtime | Versions and scopes remain consistent across transports |
| Component selection | FastAPI + generated registry | The server chooses only from explicitly registered modules |
| Rendering and interaction | React + the selected host | The browser owns presentation and local interaction state |
| Cross-worker coordination | Redis, when configured | Workers share cache data, tags, and live invalidations |

<Aside type="caution" title="The browser is not an authorization boundary">
  A hidden button is only presentation logic. Loaders and mutations must enforce authorization in
  FastAPI because every transport request can be made without your React component.
</Aside>

## A page envelope, not an HTML template

At a high level, a FluxFast response identifies the component and the current state of each
resource:

```json title="Example page envelope (version is illustrative)"
{
  "protocol": "fluxfast/1",
  "page": {
    "component": "dashboard/index",
    "url": "/dashboard"
  },
  "resources": {
    "viewer": {
      "version": "opaque-resource-version",
      "value": { "name": "Ada", "plan": "pro" }
    }
  }
}
```

You normally do not construct this object yourself. Return a `Page(...)` from a `@flux.page(...)`
handler; FluxFast resolves its resources and builds the envelope. The adapter checks the protocol,
and the browser initializes or updates the resource stores. Versions are opaque strings, not
counters. The wire record uses `value`; React's `useResource(key)` returns that value directly.
Loading/error status belongs to `useResourceState(key)`, not to this wire record.

## Pages and resources are different

<Tabs>
  <TabItem label="Page">
    A page maps a FastAPI route to a frontend component. It answers: **which interface should render
    for this URL?**

    ```python
    @flux.page('/projects/{project_id}', name='project')
    async def project_page(project_id: int) -> Page:
        return Page(
            component='projects/show',
            resources=[resource(PROJECT, lambda: load_project(project_id))],
        )
    ```

    Here `Page` and `resource` come from `fluxfast`; `PROJECT` is a declared resource contract and
    `load_project` is your application's loader. In a protected route, use FastAPI dependencies to
    authorize the project before constructing its resources.
  </TabItem>
  <TabItem label="Resource">
    A resource is typed application data with an independent lifecycle. It answers: **what data does
    the interface need, and how may it be reused or updated?**

    ```python
    PROJECT = flux.define_resource('project', Project)
    project = resource(
        PROJECT,
        lambda: load_project(project_id),
        scope=scope.custom('project', project_id),
        ttl=30,
    )
    ```

    `Project`, `load_project`, and the authorized `project_id` are application-owned values;
    `resource` and `scope` come from `fluxfast`. `define_resource` declares the value's type once.
    `resource` supplies the loader and lifecycle for a particular request. A custom scope partitions
    cached values; it does not grant project access. Add a user/tenant-specific identity if the
    serialized value differs between authorized viewers.
  </TabItem>
</Tabs>

## Choose a resource lifecycle deliberately

<CardGrid>
  <Card title="Blocking" icon="check-circle">
    Load before rendering when the data defines the page's first meaningful state. Errors become
    route-level failures.
  </Card>
  <Card title="Deferred" icon="clock">
    Render the shell first when the data is secondary or slow. The component handles loading, ready,
    and error states explicitly.
  </Card>
  <Card title="Cached" icon="database">
    Reuse loader results when a clear TTL and security scope exist. Never cache user or tenant data
    without a matching scope key.
  </Card>
  <Card title="Live" icon="refresh">
    Subscribe when canonical server changes must reach connected clients. Live data still requires an
    explicit authorization and publication scope.
  </Card>
</CardGrid>

## One public origin

In development, `fluxfast dev` starts FastAPI and its managed Next.js child process. In production,
`fluxfast build` prepares the frontend and `fluxfast start` supervises both runtimes. The browser sees
one origin:

```text
Browser
   │  http://127.0.0.1:3000 (development)
   │  https://app.example.com (production)
   ▼
Public Next.js shell + FluxFast handlers
   │  private loopback traffic
   ▼
Private FastAPI application
```

That topology removes browser-side backend URL configuration and avoids CORS between the shell and
the transport endpoints. The Python CLI supervises both processes; Next.js exposes the browser port
and forwards transport requests to private FastAPI. It also gives health checks and shutdown a
single lifecycle owner. You still have two internal processes, not two public origins.

The React/Vite host introduced in 1.2.0 uses the same topology and Python supervision. Vite provides
development HMR; a checked, built React SSR host serves production without evaluating the source
configuration or loading Vite/Codegen at startup. Follow the
[React tutorial](/FluxFast-Docs/react-getting-started/) for the separate setup and expected results.
Do not install both Next and Vite host packages in one frontend; use separate frontend projects.

## When FluxFast is a good fit

Use FluxFast when:

- your domain logic and security already belong in FastAPI;
- you want React through either the Next.js host or the standalone React/Vite host;
- pages share data that should survive navigation;
- typed Python contracts should drive frontend types and validation;
- some resources benefit from progressive or live delivery;
- you want a single-origin service rather than independently deployed browser and API origins.

FluxFast may not be the best boundary when the frontend must be independently deployed and usable
against many unrelated APIs, when offline-first local ownership is central, or when the application
does not use FastAPI and a supported React host.

## Observe synchronization during development

FluxFast 1.1 adds an optional Debugbar that reads the existing runtime without becoming part of
application correctness. Install it as a development dependency and mount it inside the existing
provider:

```bash
npm install --save-dev @fluxfast/devtools@1.2.0
```

```tsx
import { FluxDevtools } from '@fluxfast/devtools';

{process.env.NODE_ENV === 'development' && <FluxDevtools />}
```

Enable value-free server timing metadata only in your development FastAPI application:

```python
flux = FluxFast(app, debug=settings.environment == "development")
```

The inspector correlates navigation, resources, page and server caches, mutations, live recovery,
and protocol negotiation. It never displays resource values, credentials, user or tenant IDs,
request bodies, connection URLs, or patch values. See the [DevTools guide](/FluxFast-Docs/devtools/)
for the full provider example, panel semantics, safety limits, and troubleshooting.
