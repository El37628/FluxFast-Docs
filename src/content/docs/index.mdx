## One owner for application behavior

FluxFast is a server-driven application runtime, not a second API framework. Your FastAPI
application remains the authority for every route and every permission decision. The browser
receives a page envelope containing an allowlisted component name and independently managed
resources, then renders it through your chosen frontend host.

## See the model in code

Define the route and resource where the application policy belongs:

```python title="backend/main.py"
from fastapi import FastAPI
from fluxfast import FluxFast, Page, resource, scope
from pydantic import BaseModel

app = FastAPI()
flux = FluxFast(app)

class Viewer(BaseModel):
    name: str
    plan: str

VIEWER = flux.define_resource("viewer", Viewer)

@flux.page("/dashboard", name="dashboard")
async def dashboard() -> Page:
    return Page(
        component="dashboard/index",
        resources=[
            resource(
                VIEWER,
                lambda: Viewer(name="Ada", plan="pro"),
                scope=scope.public(),
                ttl=30,
            ),
        ],
    )
```

This viewer is fixed demonstration data, so public scope is intentional. For a real signed-in
viewer, authenticate in a FastAPI dependency and derive `scope.user(user.id)` from that trusted
identity—not from a browser-supplied ID.

Generate the contract, then consume the store in a registered React component:

This example uses the Next.js host. The [React/Vite tutorial](./react-getting-started/) shows the
equivalent `@fluxfast/react` imports and adapter-aware generation.

```tsx title="frontend/src/flux-pages/dashboard/index.tsx"
'use client';

import { useResource } from '@fluxfast/next';
import { resourceKeys } from '@/.fluxfast/types.generated';

export default function Dashboard() {
  const viewer = useResource(resourceKeys.viewer);

  return (
    <main>
      <p>Demo viewer: {viewer.name}</p>
      <strong>{viewer.plan} plan</strong>
    </main>
  );
}
```

```bash
fluxfast types backend.main:app --frontend frontend
fluxfast dev backend.main:app --frontend frontend
```

After completing the [initial setup](./getting-started/), open
`http://127.0.0.1:3000/dashboard`. The page displays:

```text title="Expected page output"
Demo viewer: Ada
pro plan
```

`useResource` returns the resource value directly; use `useResourceState` when you also need
status, stale, and error metadata. Continue with the [API walkthrough](./api-walkthrough/) for a
complete application with forms, deferred loading, live updates, and the corresponding JSON
request/response examples.

<Aside type="tip" title="No frontend backend URL is required">
  During development and production, the browser talks to the frontend host's origin. The managed adapter
  forwards FluxFast transport requests internally, so the application does not require a second
  public port or a browser CORS policy.
</Aside>

## Pick the right loading behavior

| Need | Use | What the user sees |
| --- | --- | --- |
| Data required for the first meaningful render | Blocking resource | Complete data in the initial page envelope |
| Expensive or secondary data | Deferred resource | Immediate page shell, then an explicit loading/error/ready state |
| Data that must update across tabs or users | Live resource | Canonical updates over a scoped reconnecting event stream |
| Reused data with a bounded lifetime | Cached resource | Shared load result within an explicit public, user, or tenant boundary |
