The latest published stable release covered by the runnable tutorials is **FluxFast 1.1.0**.
The documentation also imports reviewed development material from the application repository's
`main` branch. The **1.2.0 release candidate** is implemented and checked, but is not published yet.
Its source version and documentation are not a promise that its packages can be installed today.

<Aside type="caution" title="Stable classification is not a publication notice">
  An API's compatibility classification describes its supported contract. It does not mean a new
  export already exists in every older package. Check the section's version label and the release
  notes before copying a new import. In particular, published `@fluxfast/core@1.1.0` does not export
  `@fluxfast/core/server`.
</Aside>

## What can I use now?

| Version | Availability | What it adds |
| --- | --- | --- |
| [1.0.0](/FluxFast-Docs/releases/v1-0-0/) | Published stable | The stable FastAPI, Core, and Next.js contracts, typed generation, forms, deferred/live resources, and managed production runtime. |
| [1.0.1](/FluxFast-Docs/releases/v1-0-1/) | Published stable | Routable generated Next.js handlers and project-local agent integration knowledge. |
| [1.1.0](/FluxFast-Docs/releases/v1-1-0/) | Latest published stable documented here | Optional development DevTools and bounded runtime/server observations. Existing application APIs remain compatible. |
| [1.2.0 candidate](/FluxFast-Docs/releases/v1-2-0/) | Implemented and checked; publication pending | A complete React/Vite SSR host, shared React bindings, framework-neutral Codegen and Core server APIs, adapter-aware Python generation/supervision, and compatible Next.js integration. It is not a React host available through Python or npm 1.1.0 packages. |

The [Core reference](/FluxFast-Docs/core-api/#server-adapter-primitives-fluxfast-12) describes
the new server helpers. Until a release publishes them, ordinary applications should keep
their existing `@fluxfast/next/server` integration and generated handlers. Do not copy development
files into `node_modules` or import private package internals to make an unavailable API work.

Adapter authors can use the [Server adapter API walkthrough](/FluxFast-Docs/server-api-walkthrough/)
to test the source-built development helpers against a real backend. It includes API calls and
expected page, mutation, validation, missing-page, and path-rejection results. It is not an upgrade
instruction for a published v1.1 application.

The [Codegen API lab](/FluxFast-Docs/codegen-api-walkthrough/) shows the new offline compiler
boundary with real exported backend schema, exact API results, unsupported-validator diagnostics,
and read-only drift checks, including an explicit runtime target and a read-only page registry
scanner. The Next wrapper selects the existing Next target for applications automatically.
`@fluxfast/codegen` is also **unpublished**: its source workspace now
uses `1.2.0`, but there is no published `@fluxfast/codegen@1.1.0` package.
Use the source-build instructions in that lab rather than an npm installation command.

## Prepare for the React / Vite host

The [React tutorial](/FluxFast-Docs/react-getting-started/) starts from an empty directory and
shows complete backend and page files, generated typed resource imports, rendered output,
JSON API results, and development/production commands. The
[React API](/FluxFast-Docs/react-api/) explains the hooks and components; the
[Vite host guide](/FluxFast-Docs/vite-host/) explains setup, HMR, build artifacts, diagnostics,
and immutable production startup. You do not need to implement an SSR host yourself.

These guides require the **actual 1.2.0 packages**: Python `fluxfast`, runtime Core/React,
and build-time Codegen/Vite. Python 1.1.0 is not the supervisor for this host. Do not substitute
an older package, a bootstrap prerelease, or a private file import if a version is missing.
Next.js applications keep their existing adapter; do not add `@fluxfast/vite` to a Next frontend.

### Confirm publication before installing 1.2.0

Check the [GitHub release](https://github.com/El37628/FluxFast/releases/tag/v1.2.0),
[PyPI](https://pypi.org/project/fluxfast/1.2.0/), and every npm package:

```bash
npm view @fluxfast/core@1.2.0 version
npm view @fluxfast/codegen@1.2.0 version
npm view @fluxfast/react@1.2.0 version
npm view @fluxfast/vite@1.2.0 version
npm view @fluxfast/next@1.2.0 version
npm view @fluxfast/devtools@1.2.0 version
```

Every npm command must print `1.2.0`; the Python release and completed GitHub release must also
exist. A 404 or missing version means publication is not complete, not that you should bypass
the check. The release workflow verifies registry-only consumers before creating the GitHub
release. See the [1.2.0 notes](/FluxFast-Docs/releases/v1-2-0/) for installation and upgrade steps
**after** that confirmation. Until then, use the published Next.js baseline below.

## Install matched v1.1 packages

Activate your application's Python environment and run this from its root:

```bash
python -m pip install --upgrade "fluxfast==1.1.0"
cd frontend
npm install @fluxfast/core@1.1.0 @fluxfast/next@1.1.0
```

The optional inspector belongs in the frontend's development dependencies:

```bash
npm install --save-dev @fluxfast/devtools@1.1.0
cd ..
```

Keep your existing package manager; npm is only the example here. Matching versions across Python,
Core, Next, and optional DevTools are the recommended application baseline. Upgrade Next.js and
React within their supported ranges separately, including security patches.

### Verify the installed versions

```bash
python -c 'from importlib.metadata import version; print(version("fluxfast"))'
npm --prefix frontend ls @fluxfast/core @fluxfast/next @fluxfast/devtools --depth=0
```

The Python command should print `1.1.0`. The npm listing should show `@fluxfast/core@1.1.0`,
`@fluxfast/next@1.1.0`, and `@fluxfast/devtools@1.1.0` if you installed the inspector. Its project
name, path, and tree formatting vary. A GitHub tag, source checkout, or successful docs deployment
does not establish which package versions your application has installed.

## Regenerate, verify, and run your application

For an application with `backend/main.py` exporting `app` and a `frontend/` directory:

```bash
cd frontend
npx --no-install fluxfast init
cd ..
fluxfast types backend.main:app --frontend frontend
fluxfast types backend.main:app --frontend frontend --check
cd frontend
npx --no-install fluxfast doctor
cd ..
fluxfast build --app backend.main:app --frontend frontend
fluxfast doctor --app backend.main:app --frontend frontend --production --strict
```

Run these with the application's normal build-time configuration. `init` refreshes managed
integration files and project agent knowledge; it preserves unrelated application content.
`types` regenerates contracts from your authoritative backend declarations. Never manually patch
the generated registry, validators, route helpers, or mutation helpers to repair drift.

There are two command entry points: `npx --no-install fluxfast` runs the already installed Next
adapter's setup/generation CLI from the frontend; the Python environment's `fluxfast` runs backend
schema export, typed orchestration, and the managed runtime from the application root.

After verification, start the local production runtime:

```bash
fluxfast start backend.main:app --frontend frontend
```

Visit `http://127.0.0.1:3000` and verify your own pages and permissions, a valid and invalid form
submission, a missing page, shared-resource navigation, and any deferred/live flows you use.
The browser still uses one public origin; do not configure a browser-visible backend port.
Stop with Ctrl+C. This is a local verification step, not an instruction to deploy to production.

## Add DevTools without changing application correctness

In an application-owned client component below the FluxFast provider:

```tsx
import { FluxDevtools } from "@fluxfast/devtools";

{process.env.NODE_ENV === "development" && <FluxDevtools />}
```

Enable backend traces only through your explicit development configuration:

```python
flux = FluxFast(app, debug=settings.environment == "development")
```

Here `settings` is your application's configuration object. The client opt-in is not an
authorization override. See [DevTools](/FluxFast-Docs/devtools/) for a complete mount example,
production exclusion, data-safety limits, and troubleshooting.

## Package, protocol, and schema versions are different

Neither the published 1.1.0 packages nor the 1.2.0 candidate rename the wire protocol. The application
contract remains `fluxfast/1`; typed generation uses `fluxfast-schema/2`, with the documented
schema/1 reader compatibility. Do not derive either identifier from the npm or PyPI version.

Read the [versioning contract](/FluxFast-Docs/versioning/) for compatibility policy, the
[migration guide](/FluxFast-Docs/migration/) for older release lines, and the
[v1.1 release notes](/FluxFast-Docs/releases/v1-1-0/) for the published changes.
